Notifications: three tiers, one structure

Field crews read notifications on a lock screen, often between tasks. Each message has to say what changed and what to do in the first few words. I sorted every notification into one of three tiers, and the tier decides the channel, the tone, and whether it carries a button.

Rules I applied

Lead with the thing that changed, not a greeting. Name the object (the project, the report) so the message makes sense without opening the app. The button repeats the verb in the body, so "Review the draft" leads to a button that says "Review draft". Informational messages carry no urgency words, and exclamation marks never appear. For this sample, push titles stay at 40 characters or fewer and bodies at 90 or fewer, so they survive truncation on most lock screens.

Feature naming: name what it produces

Fieldwork can assemble a first version of an inspection report from a project's completed tasks. The feature needed a name that would work in a button, a notification, a help article, and other languages.

Criteria

The name has to be literal, so a new user can guess what it does. It has to translate, so no puns, brand coinages, or compounds that break in other languages. It has to set the right expectation, which here means the output is a draft that a person reviews. And it cannot collide with existing terms in the product.

CandidateDecisionReason
Smart reportRejected"Smart" says nothing specific, does not translate cleanly, and implies the output is correct without review.
ReportBotRejectedPersonifies the feature and builds a compound that localizes poorly.
Auto-reportRejectedHyphenation varies by language, and "auto" does not signal that review is needed.
Report draftChosenPlain noun phrase. Says what it produces and that it is unfinished. Pairs with the verbs "Create report draft" and "Review draft".

One naming rule came out of this: name the output, not the mechanism. Users manage reports; they do not manage "automation".

Localization: write strings translators can finish

Good English copy can still be unusable in translation if it is built from fragments. These are the rules I wrote for the Fieldwork string set, with the reason behind each one.

Incorrect: concatenated fragments"You have " + n + " task" + (n > 1 ? "s" : "") + " in " + project
Correct: one complete message{count, plural, one {# task is due tomorrow in {projectName}} other {# tasks are due tomorrow in {projectName}}}
RuleWhy
Write whole sentences with named variables.Word order, gender, and case change by language. Translators need the full sentence to reorder it.
Use plural messages, not "task(s)".English has two plural forms. Polish, Russian, and Arabic have more, and a plural message lets translators add them.
Format dates and numbers by locale.Pass {dueDate, date, medium} instead of typing "Oct 3".
Plan for about 30 percent text growth.German and Finnish run long. A 40-character English title needs room for roughly 52.
Avoid idioms and wordplay."Heads up" and "all caught up" rarely translate. Say "No tasks are due today."
Add a translator note to every string.Context prevents wrong guesses, such as "Draft" as a noun versus a verb.

Right-to-left check. The notification layout is designed to mirror for Arabic and Hebrew: the tier marker moves to the right edge, and the action button aligns to the start of the line. Names, numbers, and project titles keep their own text direction.

UX research plan for the names and notifications

This is a plan, not a results report. I wrote it to show how I would check the choices above before they ship. No findings are claimed.

QuestionMethodSuccess measure, set before testing
Do users read "Report draft" as a first version they must review?Unmoderated first-impression test. Show the button label (A: Smart report, B: Report draft) and ask what happens when you select it.At least 80 percent of participants on B say they would review or edit before sending.
Can users tell what to do next from a notification alone?Five-second test of the three tiers, followed by "What would you do next?"Participants name the correct next action for each tier without opening the app.
Does the copy survive translation?Linguist review of LC-01 to LC-05 in German, Polish, and Arabic, with a truncation check in the layout.No string overflows its container, and linguists flag no ambiguous terms.

Participants would be field supervisors and crew leads, recruited in small rounds of five to eight. If Smart report outperforms Report draft, I would keep the plain name and test a clearer description instead of switching to a vague one.

Figma component spec: notification

The component is built for reuse across push previews, in-app notices, and toasts. Text styles and color tokens are named by role, not by value, so the tier changes with one property.

PartSpec
Tier markerLeft edge bar plus icon. Color is never the only signal, so each tier also has its own icon and a text label for screen readers.
TitleOne line, 40 characters or fewer in English. Truncates with an ellipsis.
BodyTwo lines maximum, 90 characters or fewer. Wraps, never truncates mid-variable.
TimestampRelative and locale-formatted, such as "2 min ago".
ActionText button with a verb that matches the body. Hidden for FYI toasts.
VariantsTier (urgent, needs action, FYI) by surface (push, in-app, toast) by direction (left-to-right, right-to-left).
Auto layoutVertical stack, fixed padding, text fields set to hug so longer translations grow the component.

What I would push further

Notification volume. Three tiers help, but they do not stop fatigue. I would look at how often FYI messages are opened and consider a daily digest for that tier.

Plural categories. The plural messages are written for English. I would ask linguists to add the extra forms for each language rather than assume two are enough.

Name testing with real users. The naming criteria came from my own review. A comprehension test with field supervisors would show whether "draft" reads the way I intend.
